# Cookiecutter PyPackage 0.6.0: Clear names, safer setup, smoother releases

[WriterStead](https://writerstead.com/from/cc-py) needed a new set of Air
packages, and those packages needed a better foundation. That brought me back
to Cookiecutter PyPackage: before I could release the new Air packages, I
needed to release the template they would be built from.

Cookiecutter PyPackage 0.6.0 gives new projects clearer package and import
names, safer GitHub setup, a repeatable quality loop, and a changelog-driven
release process.

```bash
uv tool upgrade cookiecutter-pypackage
```

**Projects you have already generated remain as they are.** These changes apply
when you generate your next project. The migration notes at the end are for
saved contexts, scripts, and custom forks.

## What's new

- **Three names, three jobs.** `project_name` is the name people see,
  `package_name` identifies the PyPI distribution, GitHub repository, and
  generated directory, and `import_name` is the Python identifier. The defaults
  derive naturally from one another, but all three can differ when a package
  needs them to. Custom import names now package correctly too.

- **See the variables before you generate.**
  `uvx cookiecutter-pypackage --list-variables` shows the current prompts and
  defaults without creating a project. Documented `key=value` overrides make
  interactive and automated generation repeatable.
  ([#931](https://github.com/audreyfeldroy/cookiecutter-pypackage/pull/931),
  [#932](https://github.com/audreyfeldroy/cookiecutter-pypackage/pull/932))

- **GitHub setup waits for you.** It is off by default, chooses a private
  repository by default, shows its plan, and asks before touching Git or
  GitHub. Once confirmed, it creates the first commit, creates or connects the
  repository, and pushes `main` over your chosen SSH or HTTPS transport. It
  also prepares the PyPI environment and prints the values for registering a
  trusted publisher.
  ([#935](https://github.com/audreyfeldroy/cookiecutter-pypackage/pull/935))

- **Release from the changelog.** New projects start with
  `CHANGELOG/unreleased.md`, so changes can be recorded while they are fresh.
  `just release` turns those notes into a versioned file, creates and pushes
  the tag, and publishes the GitHub release. Branch checks and recoverable
  retries make the release less fragile.
  ([#940](https://github.com/audreyfeldroy/cookiecutter-pypackage/pull/940))

## What's better

- **One loop before you ship.** `just fix` applies Ruff's automatic fixes,
  `just check` verifies formatting, linting, types, and tests without changing
  files, and `just fix-and-check` does both in order. `just qa` remains as a
  compatibility alias.

- **Public and private repositories both work.** Pages and documentation
  deployment follow the visibility choice made during setup. Least-privilege
  workflows, conditional CodeQL, and workflow auditing support private
  repositories, while paid CodeQL features remain opt-in.

- **Setup failures are recoverable.** Declining GitHub setup leaves a complete
  local project. If a requested setup fails later, it reports what succeeded
  and what to do next. Existing nonempty repositories remain untouched.

- **One Python style in both layers.** Ruff now uses 120 columns in the template
  and the generated project, keeping mirrored code readable and in sync.
  Typer's `Option` and `Argument` declarations are handled precisely without
  weakening other default-argument checks.
  ([#949](https://github.com/audreyfeldroy/cookiecutter-pypackage/pull/949),
  [#950](https://github.com/audreyfeldroy/cookiecutter-pypackage/pull/950))

- **Current tools and pinned workflows.** Cookiecutter, pytest, ty, Zensical,
  Just, and SHA-pinned GitHub Actions are refreshed. Dependabot now applies a
  seven-day cooldown to Python dependencies as well as GitHub Actions updates.

- **Cleaner source distributions.** Generated projects ignore Zensical's
  `.cache/` directory, so building documentation before packaging does not
  ship local documentation cache files in the source archive.

- **The runtime version tells the truth.**
  `cookiecutter_pypackage.__version__` now reads the installed distribution
  metadata, so it stays aligned with the version that was actually released.

- **The documentation matches the project.** Development and release commands,
  prompt defaults, workflow coverage, CI triggers, and badge destinations are
  accurate again. The tutorial covers manual Pages and PyPI setup, distinguishes
  a first release from later version bumps, and verifies the published package
  from an isolated environment. Initial generated changelogs also remain
  accurate after their notes become a release. API reference pages discover
  documented submodules instead of stopping at the top-level package.
  ([#952](https://github.com/audreyfeldroy/cookiecutter-pypackage/pull/952),
  [#953](https://github.com/audreyfeldroy/cookiecutter-pypackage/pull/953))

## Migration notes for custom contexts and automation

If you generate interactively, there is nothing to do. Existing generated
projects are unchanged. Update only saved Cookiecutter contexts, scripts, and
custom forks.

This is not a one-to-one rename: 0.6.0 consolidates the distribution,
repository, and generated directory under `package_name`, while reserving
`import_name` for Python.

| Earlier context | 0.6.0 | Responsibility now |
|---|---|---|
| `pypi_package_name` | `package_name` | PyPI distribution, GitHub repository, and generated directory |
| `project_slug` | `import_name` | Python imports and the generated CLI command |
| `github_username` as repository owner | `github_repo_owner` | GitHub user or organization that owns the repository |

Previously, the package and import-style names could both appear in GitHub
references: some links used `pypi_package_name`, while the private `__gh_slug`
was built from `project_slug`. New projects use
`github_repo_owner/package_name` consistently for GitHub, documentation, and
security URLs.

For example:

```bash
# Before
uvx cookiecutter-pypackage --no-input \
    pypi_package_name=my-package \
    project_slug=my_package

# 0.6.0
uvx cookiecutter-pypackage --no-input \
    package_name=my-package \
    import_name=my_package
```

`github_repo_owner` defaults to `github_username`, so personal projects need
no extra configuration. Set it explicitly when the repository belongs to an
organization:

```bash
uvx cookiecutter-pypackage --no-input \
    github_username=yourhandle \
    github_repo_owner=your-organization \
    project_name="My Package"
```

Custom forks that referenced the private `__gh_slug` variable should construct
the repository path from `github_repo_owner` and `package_name` instead.
